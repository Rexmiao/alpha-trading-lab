# 每日信号采集与自动交易系统实施规格

版本：0.2.4；日期：2026-11-26；状态：实施设计，M1 尚未实现。

用户目标：一套系统共用数据、因子、信号、组合、风控与审计，可选择仅提醒、人工确认执行、自动执行；最终支持真实资金自动化交易；初期先每天稳定采集真实行情、计算因子、捕捉信号并留档。本文件定义后续实现顺序及验收条件，不把现有研究网页或订单草稿描述成已具备实盘能力。当前已实现范围见[主 SPEC](../SPEC.md)。

## 1. 系统类型与本项目定位

下面是可组合的策略组织方式，不是互斥分类：

| 方向 | 主要研究对象 | 本项目安排 |
| --- | --- | --- |
| 规则型 | 趋势、动量、短期反转及量价条件 | 作为可解释的因子和工程基线 |
| 多因子／机器学习型 | 多种信息对未来收益或排序的预测 | 主线；保留 Ridge、MLP 及生成增强对照 |
| 事件驱动型 | 财报、指引、公告等事件发布后的机会 | 后续加入有真实发布时间的文本因子 |
| 统计套利型 | 配对、价差和相对定价偏离 | 独立研究阶段，另定义对冲及成本 |
| 做市型 | 报价、买卖价差和库存管理 | 不属于本次日频系统范围 |

另有两个独立维度：频率可以是日频、日内或更高频；自动化范围是同一系统可选择的执行策略：仅提醒、人工确认后执行、自动执行，三者不拆成三套策略程序。本项目目标组合是“美股日频＋多因子／深度学习预测＋最终全自动实盘”。每日只计算一次，也可以形成自动化交易系统。

VWAP、TWAP 等属于订单执行方法；其作用是处理既定订单的成交过程，不能单凭执行算法证明有预测 alpha。参见 [CFA 的交易策略与执行说明](https://www.cfainstitute.org/insights/professional-learning/refresher-readings/2026/trade-strategy-execution)及 [SEC 算法交易报告](https://www.sec.gov/about/reports-publications/algo_trading_report_2020)。

## 2. 一套系统、可选模式与交付阶段

数据采集、特征、模型、组合、风控、状态与审计共用。所有模式均可发提醒及日报；模式决定交易提案如何进入提交环节，不改变预测算法或绕过风控。

### 2.1 两个独立选择

| 执行策略 automation_mode | 行为 | 是否提交新订单 |
| --- | --- | --- |
| ALERT_ONLY：仅提醒 | 显示信号；组合能力具备后可显示同一交易提案与原因 | 不发起新提交／模拟成交任务；已在途生命周期继续 |
| CONFIRM_BEFORE_SEND：人工确认执行 | 生成有效交易提案，用户确认后复核并提交 | 仅提交确认内容允许的订单 |
| AUTO_EXECUTE：自动执行 | 对新生成且有效的提案，风控通过后自动提交并报告结果 | 按预先配置的策略自动提交 |

| 账户／执行环境 execution_environment | 含义 |
| --- | --- |
| NONE | 未连接执行环境，仅采集与提醒；只允许 ALERT_ONLY |
| SHADOW | 本机独立影子账本，确认／自动模式只产生模拟成交 |
| BROKER_PAPER | 已核实的券商模拟账户 |
| LIVE | 已明确配置的真实资金账户 |

因此“自动执行＋影子账本”“人工确认＋券商模拟”“仅提醒＋已配置实盘账户监控”都是同一系统的组合，不把“自动”等同于“真钱”。未来实盘自动执行是 AUTO_EXECUTE＋LIVE。

workflow_kind=CAPTURE／REPLAY 描述数据处理任务，与上述两个选择分开。REPLAY 使用独立命名空间，不能进入券商模拟或实盘提交路径。

### 2.2 阶段代表能力交付，不是四套模式程序

| 阶段 | 新增能力 | 可开放的组合 |
| --- | --- | --- |
| M1 | 每日数据、因子、事件、固定模型推理和审计 | CAPTURE＋ALERT_ONLY＋NONE；另有独立历史 REPLAY |
| M2 | 共同的组合／风控提案、确认机制、分发器和持续影子账本 | SHADOW 环境下三种执行策略；NONE 下仍仅提醒 |
| M3 | 券商模拟适配、订单回报与对账 | 已实现并核实账户后的 BROKER_PAPER＋三种执行策略 |
| M4 | 实盘适配及真实账户风险、运行与恢复约束 | 已配置的 LIVE＋三种执行策略 |

缺少对应能力、账户或风险配置时，相关组合保持不可用并显示原因，不能用改配置绕过阶段条件。未来控制台使用一个“执行方式”选择器和一个“账户环境”选择器；公开教学网页仍保持研究边界，交易控制放在本机／私有控制台，共用同一策略引擎。

本轮交付是规格文件，尚未创建任务、数据库或新交易代码。M1 不读取资金／持仓、不实例化执行适配器、不调用订单方法；其记录始终 trade_eligible=false。未来 LIVE 的启用与账户配置独立于执行方式切换；普通订单在已启用的权限和风险范围内按所选模式运行，不要求自动模式逐笔人工确认。

M1 的完成标准是每天正确取得并保存记录，包括“为什么没有可用预测”；不要求每日都有买入信号，也不以正收益判定工程通过。

## 3. 复用现有代码与新增组件

已有能力：moomoo 只读采集、日 K 规范化、41 项价量特征、按时间切分与标签 purge、模型 artifact、四模型实验、EWMA 风险约束、整数股草稿及次开盘离线回测。

当前[一次性研究入口](../research/pipeline.py)每次实验会训练模型，草稿使用独立空仓假设；它不承担每日常驻服务或持续持仓记账。新组件不直接调用 run_experiment() 来完成每日任务。

计划新增 trading_system 包：

| 模块 | 职责 |
| --- | --- |
| calendar.py | 交易日、提前收市、时区与任务资格 |
| capture.py / sources/moomoo.py | 只读采集、超时、限频、来源契约 |
| snapshots.py | 不可修改的原始响应、规范化行情和哈希清单 |
| factors.py | 有版本的因子定义、缺失状态及事件判定 |
| models.py | 可信模型注册、版本固定和日常推理 |
| signals.py / outcomes.py | 每日发布、信号时点及成熟标签 |
| store.py / migrations | SQLite 状态、唯一键、事务及任务租约 |
| daily.py / reports.py | 流程编排、补跑、健康状态和本机报告 |
| policy.py | 共用执行策略／环境配置、能力检查及 policy_epoch |
| proposals.py / approvals.py / dispatch.py | M2 起共用的交易提案、确认与提交分界；不复制策略引擎 |
| portfolio / ledger / execution | M2–M4 后续组件，M1 不实例化执行适配器 |

主流程：

```mermaid
flowchart LR
    A[交易日与任务资格] --> B[只读行情采集]
    B --> C[快照与质量检查]
    C --> D[因子与事件]
    D --> E[固定模型版本推理]
    E --> F[信号与审计存储]
    F --> G[本机日报]
    F -. 后续阶段 .-> H[组合与风险]
    H -.-> P[同一交易提案]
    P -.-> Q[仅提醒 人工确认 自动执行]
    Q -.-> I[委托 成交 对账]
    I -.-> G
```

源码和规格继续放在当前 D 盘项目；活动数据库由 ALPHA_RUNTIME_DIR 指向本机非同步目录。HF／Streamlit 保留研究演示职责，不携带该运行数据库或券商凭据。

## 4. M1 固定起点

- 初始选择：workflow_kind=CAPTURE、automation_mode=ALERT_ONLY、execution_environment=NONE；只启用每日采集与提醒能力。
- 市场：美股股票／ETF、USD、日频；时间计算使用 America/New_York，持久化时间统一 UTC。
- 首批股票：NVDA、AMD、AVGO、MU、WDC、SNDK、NBIS、CRWV；基准 SPY。它们是研究池，不冒称用户持仓。
- 股票池、上市／业务重启边界、数据源和因子定义均有版本。可复用[现有股票池边界](../config.json)，新增股票必须显式变更版本。
- 主源：现有 moomoo 桌面只读链路。Yahoo 等源作为单独研究配置，不自动替代 moomoo，也不混合复权口径。
- 预测期限：首个运行策略固定 h=5。研究网页仍可调 1–20；运行系统改变 h 时需新策略／模型版本。
- 每天采集并计算，不代表每天调仓。M2 才根据固定锚点每五个交易日生成一次组合决策。
- 初始没有 active model 时仍采集数据、因子和事件，预测状态为 NOT_CONFIGURED。首个工程基线可注册可信 Ridge artifact，不能因此称其已具备有效 alpha。

## 5. 每日时间与调度

### 5.1 交易日历

使用有版本和来源哈希的美股交易日历，按官方交易时间复核；不能用周一至周五或固定 16:20 代替交易所日历。日历缺失、过期或范围外时阻止正式发布，保留诊断。

首次尝试在交易所计划收市后 20 分钟开始；这段缓冲是项目策略，不保证供应商数据已经最终修订。数据完结方法及供应商返回状态分别记录。

官方例子：2026-11-26 休市，2026-11-27 股票市场于美东 13:00 提前收市，因此该日首个资格时点为 13:20，而不是固定 16:20。参见 [NYSE 官方日历](https://www.nyse.com/trade/hours-calendars)。

### 5.2 计划调度方式

实施时由本机调度器每五分钟唤起轻量检查：查日历、数据库和租约后，只有待采集的合格交易日才访问行情服务。已完成日期直接幂等返回，不重复请求完整股票池。

正常尝试时点为收市后 +20、+35、+60 分钟，最多三次；正式及时窗口到收市后 +90 分钟。该上限按业务键跨重启持久保存，普通重试与自动迟到补跑共用三次额度，五分钟唤起不能重置计数。单次总任务预算 15 分钟，子请求另设超时并遵守来源限频。限流遵守来源要求；认证、配置和字段契约错误不做快速重试。

PC 休眠、桌面未登录或 Host 不可用须报告 BLOCKED／FAILED。M1 不假定本机全天在线；无人值守服务的运行账户和主机稳定性在实盘前另行验收。

默认只自动补最近一个遗漏的合格交易日，并保留真实生成时间及 LATE_CAPTURE 标记。自动补跑仅在该日期仍有剩余额度时进行，迟到重试至少间隔15分钟，超过及时窗口必须标为迟到；额度耗尽后保持阻止状态，需有理由和有限次数的操作员追加尝试记录。更久补采使用显式 REPLAY／backfill 流程，不能倒填成当天曾经发出的信号。REPLAY 使用独立命名空间，不占用或改写 CAPTURE 正式发布指针，也不混入前瞻评价。休市当天如果上一合格日已完成，不产生新的交易日批次；遗漏上一日时允许按补跑规则取得历史数据。

### 5.3 任务状态

PLANNED → COLLECTING → VALIDATING → FACTORIZING → PREDICTING → COMMITTING → COMPLETED。

任一步可进入 BLOCKED 或 FAILED。数据、因子、预测分别保存组件状态：例如数据和因子完成但模型未配置，不伪装成预测成功。正式批次整包原子发布，不暴露半份预测。

## 6. 数据契约与时点

每份快照至少记录：snapshot_id、source_profile、源证券代码／稳定身份、请求参数、session_definition、price_basis、request_started_at、received_at、原始文件 SHA256、规范化文件 SHA256、日历／股票池版本及质量状态。

日 K 标准数值列沿用 date,symbol,open,high,low,close,volume；时点、来源及质量放在配套清单，不将它们猜成价格字段。

必须区分四个时间：

| 字段 | 含义 |
| --- | --- |
| signal_session / event_time | 对应哪个市场交易日及已结束的行情时段 |
| observed_at | 本机实际取得响应的 UTC 时间 |
| available_at | 可证明的最早可用时间；无供应商发布时间时保守使用 observed_at |
| created_at | 实际生成因子／预测的时间，不能改成历史交易日 |

正式信号只能使用生成时已经取得、所属交易日不晚于信号日的数据。今天打开一个昨天盘中采集的文件，不能把当时未完成 K 线升级成完整日 K；需重新采集收市后的版本。

当前桌面日 K 的 RTH／扩展时段语义如未独立核实，应标记 PROVIDER_DAILY_UNVERIFIED，作为研究采集保存；不把它标成已可用于实盘成交的 RTH 价格。数据质量合格、时段语义和未来交易资格是不同字段。

价格口径至少区分 adjusted_research 和 raw_execution_reference。研究复权 OHLC 不作为实盘报单价格；M1 即使只有前复权日 K 仍可保存研究记录，但缺少 raw 价与公司行动约束时不能启动后续货币账本或实盘执行。

### 6.1 不可修改与修订

- 原始响应、规范化数据和清单按内容及采集批次保存，不覆盖旧文件。采集适配须输出到本次 attempt 私有目录，不能依赖会被其他研究任务改写的 data/manifest.json；保留既有研究命令兼容性。
- 同日重取价格变化形成新 snapshot_id 和 supersedes 关系；旧信号和使用的旧快照保持不变。
- 原始响应哈希与规范化数值哈希分开，避免把仅响应元数据变化当成价格修订。
- 已发布日期的修订不得自动替换正式信号；保留研究修订及差异记录，后续实盘消费者不会据此重复交易。
- 首次回填的多年历史是“事后取得的历史”，不是已证明的历史时点数据；真正的逐日可见性证据从日常采集开始积累。

### 6.2 质量门槛

拒绝重复证券／日期、非有限值、非正价格、负成交量、矛盾 OHLC、缺基准及错时区／币种。不得填补上市前或停牌缺失行情。

首版要求固定股票池全部所需证券完成当日数据和特征。部分成功保留在诊断区，不伪装成完整横截面。新增股票历史不足须显式标记；变更可投资名单通过有版本的规则处理。

超过 30% 的单日变动作为复核标记，不能单凭幅度删除。错误、过期与未配模型不能转成零分、空股票池或“清仓／现金”信号。

## 7. 因子与事件捕捉

优先复用[现有特征定义](../research/data.py)，第一批重点监控如下。C 为同一研究口径收盘价，B 为基准，交易日下标来自基准日历。

| 因子 ID | 定义 | 用途 |
| --- | --- | --- |
| relative_momentum_5_v1 | C(T)/C(T-5)-1 减去 B 同期收益 | 相对强弱假设 |
| momentum_20_v1 | C(T)/C(T-20)-1 | 趋势假设 |
| reversal_5_v1 | -(C(T)/C(T-5)-1) | 短期反转假设；新研究因子 |
| volume_ratio_20_v1 | V(T)/mean(V(T-19)..V(T))-1 | 放量程度；窗口包含当前已完成日 |
| vol_20_v1 | 最近20个日收益的样本标准差，ddof=1 | 风险指标，不自动解释为 alpha |

每个值保存 factor_id/version、单位、窗口、角色、快照、值或空值、状态、最大输入时点及 computed_at。缺少必要窗口记录 INSUFFICIENT_HISTORY，不填零。

M1 还可记录 EXTREME_HIGH／EXTREME_LOW 事件：默认从本次快照计算 T 之前最近60个基准交易日的同版本因子值，要求60点均有效；排除当日，采用线性插值的 90%／10% 分位数。阈值值及其快照一起保存；历史不足时只保存值，不生成阈值事件。严格大于上阈值为 HIGH、严格小于下阈值为 LOW，等于阈值为 NORMAL；两阈值相等时标记 DEGENERATE_THRESHOLD，不生成极值事件。事件表示观察到极值，不等于买卖建议。

事件跨日重复与首次越界分开：每天保留极值状态，只有前一个基准交易日已有正式、有效、同因子／阈值策略版本状态，且本日进入 HIGH／LOW，才记录 ENTER_HIGH／ENTER_LOW；缺前一交易日或换版本后只记状态，不跨缺口推定首次越界。阈值方法、样本窗口和比较规则均有版本；不得按当前测试收益调阈值后重写旧事件。

捕捉用的新因子不自动注入现有41维模型。模型输入名称、顺序和变换须与其注册特征结构完全一致；换结构需重新训练并注册新版本。

后续文本因子另记录公告／财报的实际发布时间和抓取时间，GenAI 提取结构化字段或做训练期增强；不能用财报覆盖季度代替信息公开日。LLM 输出通过信号与风险规则处理，不直连订单调用。

## 8. 模型、预测与标签

### 8.1 日常推理

每日读取已登记的 active model 并调用 predict()，不运行 fit_predict_models()。artifact 连同 scaler、特征顺序、标签定义、训练数据哈希、seed、代码／依赖版本及权重 SHA256 固定。

只加载本机可信、已登记且哈希一致的 artifact；网页访客不能上传模型。没有 active model 仍完成数据／因子采集，模型组件为 NOT_CONFIGURED；哈希、特征、h、基准、研究价格口径、日 K 时段或来源契约不匹配则为 MODEL_INCOMPATIBLE；来源迁移仅允许已登记并有验证记录的兼容映射，不自动用另一模型冒充。

score_kind 必须区分 raw_factor、rank_score、expected_excess_return。直接回归收益的输出须逆变换恢复原收益单位；无收益单位的 ADNN 等排序分数须经独立验证期校准，才能参与收益／成本门槛。具有收益单位仍不等于统计校准良好或预测有效。M1 保存数值、单位和原因，不生成订单。

### 8.2 独立训练与切换

候选模型训练是单独任务。训练时仅使用截止时点已经可见、标签已经成熟的数据，继续按 label_end purge。MLP、重采样与 DDPM 对照使用预先规定预算，生成器只见训练集。

注册记录训练／验证边界及标签可用截止时间；激活记录明确 effective_from_session、旧／新版本和原因。业务任务创建时原子固定 model_version（或 NO_MODEL），该日后续阶段及重试始终沿用此版本，不重新读取 active 指针。激活不回溯到已创建任务或已发布的交易日；新版本用于之后合格的任务。已发布信号永久保留原模型版本。M1 可手动激活已验证候选；不得仅因最新测试收益最高而自动晋升。

### 8.3 h5 语义与成熟

现有标签严格为 T+1 开盘至 T+6 开盘的股票收益，减去 SPY 同区间收益。不是 T+5 收盘，也不是五个日历日。

只有两端股票与基准价格均已实际取得并可见，才能追加 label_outcome。只有日 K 采集时，T+6 开盘已经发生也可能要等当日采集后才能登记；不能按时间经过自动标成熟。

计算标签的两端价格必须来自同一兼容复权／公司行动版本，不能拼接两个不同复权基准的价格。标签记录 entry/exit session、price_snapshot_id、observed_at 和版本；不回写原信号。后续价格修订另增标签版本。

### 8.4 研究评价

记录成熟标签数量、有效股票数、逐日 Rank IC、分时窗稳定性及后续含成本 P&L。每日重叠五日标签不能直接累加成净值，其统计不确定性需考虑时间相关。

同一天所有股票减去相同 SPY 收益不会改变横截面排序，因此 Rank IC 不能证明已剔除行业或 beta。行业／beta 暴露单列研究，估计只用历史数据。

相对收益预测也不是绝对上涨预测；未来组合层须明确跟踪基准、市场／行业风险及现金政策。当前真实历史实验不支持直接宣称已发现有效 alpha，M1 工程验收与盈利检验分别进行。

证券身份和 universe_version 可以先使用有版本配置，不以当前 ticker 字符串代替长期证券身份。

### 9.2 幂等规则

CAPTURE 业务键为 (strategy_id, market, signal_session)，每个键只有一份正式发布批次。REPLAY 使用 (replay_scenario_id, strategy_id, market, signal_session, fingerprint) 的独立命名空间，不能写 CAPTURE 发布表；未来各执行环境和账户的订单账本也独立隔离。执行端 decision_cycle_id 绑定策略、正式信号／调仓周期、环境和账户，不包含 automation_mode；模式切换不能制造重复执行周期。

计算指纹包含规范化快照、模型或 NO_MODEL、特征结构、因子／阈值策略、股票池、研究配置、日历及代码哈希。研究配置哈希与执行策略哈希分开；automation_mode、execution_environment 和 policy_epoch 不进入捕捉业务键／研究计算指纹，切换执行方式不产生另一份行情或预测。同键同指纹重跑返回已有结果；同键不同输入只能创建显式修订，不能静默改正式发布指针。外部数据是否刷新另有动作，不由普通重跑触发。

唯一约束负责最终去重；进程内锁不足以保证重启／多进程一致性。使用数据库任务租约、递增 fencing token，旧执行者失去租约后不能提交正式批次。

### 9.3 文件与事务

1. 网络采集和计算在短写事务之外执行；文件先写 staging。
2. 完成文件数据持久化、哈希核对及同卷原子重命名后，才在数据库登记为 AVAILABLE；文件须 flush／fsync，目录元数据按平台能力持久化并记录限制，不能把 rename 等同于断电保证。
3. 因子、信号、文件引用和完成状态在同一发布事务提交；读取方仅见已提交正式批次。
4. 文件成功但事务失败会留下孤立 artifact；恢复时核对清单，不能误认成已发布信号。
5. 进程在提交后退出，重启须识别已完成批次并核对引用文件的存在性／哈希后返回；不能重复发布。
6. 启动时及消费前检查正式批次引用文件完整性。已提交后丢失／损坏文件时追加完整性故障并隔离消费，原预测数值不改；不能只看 COMPLETED 就报告成功或自动伪造文件。

M1 采用同机单写者、SQLite 外键、journal_mode=DELETE、synchronous=FULL 及有限 busy_timeout；记录实际 sqlite3.sqlite_version。活动 DB／journal 放在本机非同步目录，不直接放 Dropbox。WAL 可在后续经过并发和恢复验证后启用，须使用已修复 WAL-reset 问题的 SQLite（3.51.3 及之后，或经核实的补丁回移版本），不假定现有 Python 自带版本满足要求。备份使用一致性备份方式后，才可复制已完成备份到项目存档。参考 [SQLite WAL](https://sqlite.org/wal.html)与[Backup API](https://sqlite.org/backup.html)。

## 12. 统一执行机制与后续能力

### 12.1 共用提案与执行策略

同一信号、研究配置、账户状态、报价及风险规则必须产生相同的交易经济内容（买卖方向、数量与价格约束），不能因为选“提醒”或“自动”而另跑一套选股／风控。切换后新建提案的 ID、policy_epoch、时间及模式元数据可以不同，不能复用旧确认。环境或账户余额不同可以产生不同提案，但必须记录输入差异。

提案至少绑定 proposal_id、decision_cycle_id、revision、不可变内容哈希、正式信号 ID、模型／研究版本、环境、账户、买卖方向、数量、订单类型、限价／允许价格范围、费用与资金上限、有效窗口及执行策略版本。

- ALERT_ONLY：保存并展示提案，标记 NOT_DISPATCHED；不把旧提醒保留为待自动执行队列。
- CONFIRM_BEFORE_SEND：有效提案进入 PENDING_CONFIRMATION。确认绑定具体内容哈希、环境、账户、数量／价格约束及截止时间；同一确认最多使用一次。拒绝、过期、内容变化或执行策略失效时，不提交。
- AUTO_EXECUTE：新有效提案在相同风控、去重和提交规则下执行，结果同样进入提醒、订单状态及对账流程。自动执行不等于忽略数据或风险条件。

确认后与自动提交前均须复核最新报价、账户／未完成订单及风险。报价在原提案允许范围内且订单内容不变时可以继续；超出范围、目标数量／账户／重要条件变化时生成新修订，半自动模式重新确认。h=5 是预测期限，不是提醒可在五天内任意补执行的许可；信号、提案和确认各有明确 valid_until，提案及确认不得超出原执行窗口。

### 12.2 模式切换与提交分界

首版使用一个明确的策略执行配置（execution_profile）；影响该配置的模式、环境、账户或关键风险参数变化，原子生成新 policy_epoch，记录操作者、原因、旧／新配置及生效时间；已保存信号、提案、确认与订单保留其原版本。

| 切换或事件 | 处理规则 |
| --- | --- |
| 仅提醒 → 人工确认／自动 | 仅作用于生效后新建、仍在有效窗口内的提案；旧提醒不补执行 |
| 人工确认 → 自动 | 旧待确认提案失效，不自动放行确认队列 |
| 自动 → 仅提醒 | 阻止新的提交，不默认撤销已发订单或清仓 |
| 环境／账户变化 | 原未提交提案及确认失效；重新取得目标账户状态、报价和风险配置 |
| 模拟 → 实盘 | 不能自动绑定真钱账户或继承模拟资金配置；须满足 LIVE 能力和账户启用条件 |
| 实盘 → 模拟／NONE | 新提案按新环境处理；已有真实订单仍按原环境、原账户维护回报和对账 |
| 提案过期、内容改变或策略撤销模型许可 | 旧确认失效；如需行动则重新形成提案，不能修改已确认内容后发送 |

模式变更不重新训练模型或改写日信号；未过期的信号可用于之后合法的新提案，但必须重新取得报价和风险上下文。改变未来模型激活记录也不修改已固定的信号版本，是否允许某模型执行由提案所属策略许可检查。

提交分界为持久化 dispatch claim：在一个短事务内校验 epoch、暂停状态、提案哈希／有效期、风险检查和一次性确认，并原子检查执行请求仍未领取、将其改为 SUBMITTING，再在事务外调用适配器。稳定 execution_request_key 由 decision_cycle_id、环境／账户、证券及明确的调仓委托分段编号确定，设数据库唯一约束；不能由随机 intent_id 或新 revision 产生另一个去重键。同请求重试返回已有 intent，并发 worker 最多一个领取成功；新修订必须计入已成交和在途数量，不能用新 ID 重复执行同一调仓意图。切换和 claim 串行化；先切换的旧 epoch 不能 claim，先完成 claim 的订单属于在途，模式切换不能保证其未被券商受理。

SUBMITTING／SUBMISSION_UNKNOWN 继续按原账户查询和对账，不因切换而标成“未发送”、本地取消或直接重发。已提交／部分成交订单的剩余量参与后续净差计算。暂停执行是单独运行状态：暂停新提交时，数据采集、信号、提醒、成交回报与对账仍继续。

### M2：持续影子账本

固定五日调仓锚点，失败或重启不能移动锚点。日常捕捉仍每天发生，净值来自单一持续账户，不把每日重叠五日收益相加。

现金、持仓、委托和成交使用明确精度；每笔成交、费用与余额改变在同一事务记录。净委托量考虑已持数量和有方向的未完成数量：已持10股、目标12股且无待成交时只增2股。

真实货币账本需要未复权价格、费用及公司行动处理。缺少可核实拆股／分红／碎股处理时，不把复权研究组合当成美元实盘账本。先用有明确价格与公司行动范围的工程样本验账。

### M3：券商模拟适配

单独选择并实现一种正式支持的 moomoo 路线；现有桌面 CLI 凭据和只读方法不能直接当作交易 SDK 凭据。账户、模拟环境、订单／成交回调需独立核对。

保存 CREATED、SUBMITTING、ACKNOWLEDGED、PARTIALLY_FILLED、FILLED、CANCEL_PENDING、CANCELLED、REJECTED、SUBMISSION_UNKNOWN 等状态；以实际回报为准。超时不代表未受理，先查询／对账；不能盲目重发，也不假定 remark 是券商提供的幂等键。

moomoo 官方接口提供模拟环境，但 place_order 参数默认 REAL；适配器必须显式指定模拟环境和已核实账户，不能依赖默认账户索引。[官方接口](https://openapi.moomoo.com/moomoo-api-doc/en/trade/place-order.html)、[账户列表](https://openapi.moomoo.com/moomoo-api-doc/en/trade/get-acc-list.html)。

### M4：真实资金自动化

实盘环境在同一系统内使用独立适配器、明确账户映射、策略资金上限及用户定义的风险参数；不把研究中的100000模拟资本当作真钱预算。启动和重启先核对现金、持仓、未完成订单及成交，出现不一致先暂停新委托。

完整链路为信号 → 预期收益／目标仓位 → 风险检查 → 新鲜原始报价 → 净股数 → 订单 → 成交 → 对账。隔夜开盘价在前一晚未知，未来选定的执行政策必须重做匹配回测，不能把知道次日开盘价的回测换仓直接搬到前一晚报单。

停止新委托、撤销未完成订单和主动清仓是三个不同动作；数据失败默认不会自动变成强制清仓。紧急停止、连接故障、过期信号、撤单中及提交结果未知均须有可演练流程。

进入本阶段前再确定账户地区／权限、真实资金预算、最大仓位／行业与市场暴露、损失限制、订单类型、报价新鲜度及无人值守运行要求。本文件不虚构这些尚未确定的实盘参数。

### 13.1 开发方式与框架参考

本项目当前选择 Python 模块化单体：同一源码项目内按职责划分 trading_system 包，以明确的数据对象连接模块，先在本机单进程运行。研究训练与每日运行是独立入口；行情、日历和后续执行通过适配器接入，UI 只读取已发布结果。此选择依据当前美股日频、八股＋SPY、moomoo 桌面链路和已有研究代码，不表示所有量化团队采用同一架构。

参考公开框架的设计原则，而非本阶段引入整套框架：

| 官方参考 | 可借鉴部分 | 本项目用法 |
| --- | --- | --- |

### 13.2 首个端到端交付

首个可运行增量贯穿 M1-A/B/C/D 的最小必要部分，不逐个模块写完后才做集成，也不代表完整 M1 验收完成：

1. 显式读取运行配置和有来源的交易日历，判断目标日与采集资格。
2. 通过现有只读 moomoo 路线采集八股＋SPY，每次尝试使用独立目录。
3. 冻结原始响应、规范化数据和来源／时点清单，质量检查通过后登记 SQLite 状态。
4. 计算第7节的五项有版本因子与适用的事件，保存空值的明确原因。
5. 初始无 active model 时，预测组件显示 NOT_CONFIGURED，不以零分代替；此增量不训练候选模型。
6. 原子发布可追溯的本机中文／英文日报，说明交易日、实际取得时间、覆盖、因子变化与异常。

命令名称仍以第10节计划 CLI 为准；当前尚无 trading_system 运行命令。先用手工单次运行验证，再在 M1-D 接入本机调度；本文件的修改不注册后台任务。完整 M1 仍须补齐固定模型注册／推理、成熟标签、恢复和全部 C01–C25，并积累十个真实交易日记录。

### 13.3 按契约和验收组织小批次

- 先固定输入输出：MarketSnapshot、FactorObservation、SignalBatch 的字段、版本、时间和错误状态与第6–9节一致；DecisionProposal 在 M2 引入，避免计算层直接访问券商。
- 将因子、特征和风险计算尽量写成明确输入输出的函数；存储、时钟和行情访问通过接口传入。历史重放与每日运行复用同一因子定义，但保留独立命名空间和已可见时间检查。
- 每一批提交只覆盖一个可评审行为及对应验收。首个增量重点演练完整九代码、同日重跑、盘中旧文件、缺失／坏数据、未配模型、并发与崩溃恢复（C01、C02、C04、C07、C09、C14–C16）；其余场景不能因此标记通过。
- 对时间边界、去重、恢复、标签成熟及资金／订单状态写行为测试；使用固定时钟与自建小样本复现异常，测试不依赖可用的券商凭据或外部行情。再用私有真实快照做集成验证，分别记录测试结果和真实采集证据。
- 先约定模块接口，再并行开发互不重叠的文件；接口、状态迁移、账户和资金语义做独立复核。AI 可以辅助实现和生成测试，但产出须经过运行、边界验收和代码评审，生成成功不等于验证通过。
- 每次变更同步实现状态、依赖和复现说明。提交保持小批次，自动检查使用非真实市场样本；真实行情、活动 DB、模型、账户与密钥不进入仓库或 CI。

### 13.4 研究、每日运行和展示的配合

研究入口负责候选模型训练、按时间验证与冻结 artifact；每日运行入口负责最新数据、固定版本推理、信号留档和健康状态；本机／私有控制台读取正式批次，后续承载统一执行模式控制。公开 HF／Streamlit 继续展示研究实验，不承载券商账户或运行数据库。

第一阶段评估的是每天能否留下可信记录：该有的数据有没有取得、发生异常能否解释、同一输入能否重放、重启是否重复发布。IC、含成本收益和风险暴露用于另外的策略评价；十天工程运行记录不能证明策略盈利。通过 M1 后，按原计划增加持续影子账本、券商模拟及实盘能力。


### 13.5 框架优劣与采用门槛

2026-11-26 已完成文档、固定源码、发布与包元信息研究，详见[LEAN／Qlib／NautilusTrader 比较](../docs/FRAMEWORK_COMPARISON.md)。尚未安装、进行跨框架性能测试或券商联调；当前 M1 继续采用既定 Python 模块化实现路线，不新增框架依赖。

研究适配先评估 Qlib 的模型接口和实验管理；美股回测／执行以 LEAN 作候选对照；NautilusTrader 保留为未来事件驱动执行候选。采用范围通过固定数据、相同标签／成本和恢复案例的小实验决定，不以宣传性能或默认回测收益决定。

必须显式处理：Qlib 默认标签／标准化分数与本项目 h5-SPY 收益单位不同；LEAN 的默认补值／复权与 moomoo 接入需核实；Nautilus 稳定1.x与latest文档2.x不能混用，且当前公司行动范围及依赖冲突影响美股实盘选择。发现第三方 Futu 适配不代表我们当前桌面 Host 已兼容，也不改变现有认证和执行权限。

所有候选均须保持信号／执行分离、冻结模型版本、数据可见时间、正式批次不可修改及模式切换验收。进入 M2／M3 前比较成熟引擎与自建维护成本；本轮研究不把完整订单管理默认交给自建，也不把现有研究网页升级成交易控制台。


### 13.6 已有规则研究与运行系统的关系

0.6.0研究应用新增四种日频动量／趋势规则、共同窗口离线回测和双语页面，定义及分钟研究边界见[策略文档](../docs/MOMENTUM_TREND.md)。规则因子与可执行状态可以作为后续M1/M2的可解释对照，但当前网页使用会话内行情和离线模拟，不提供每日任务、持久化账户或交易分发器。M1–M4的计划与验收要求保持不变，公开网页不因新增规则变为实盘控制台。

### 13.7 执行框架候选补充

用户希望复用实际交易框架，候选对比见[选型研究第9节](../docs/FRAMEWORK_COMPARISON.md)。在保留moomoo／Python的前提下，优先验证VeighNa的组合策略与独立Futu适配；现有Futu插件较旧，OpenD／桌面Host、账户实体、时区、pandas分页和订单类型均未通过本项目验收，不能承诺直接实盘。若改用LEAN已有支持的美股券商，LEAN的优先级提高；Freqtrade与PandoraTrader当前不匹配市场和开发目标。

这是一项待验证的候选排序，不是已完成框架迁移。HF仍是研究入口，执行运行环境和活动账本置于本机／私有服务。模型与策略逻辑保留独立接口，不因引入框架修改预测单位或跳过共同风控；执行层维持唯一订单真相。任何模拟账户接入与实盘激活仍按M3／M4各自前提处理。
